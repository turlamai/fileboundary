# Testing

Testing is the project's evidence system. The rules here are enforced in review ([`AGENTS.md`](../AGENTS.md)); from [Issue #6](https://github.com/turinglambdaai/fileboundary/issues/6) onward they are enforced by CI.

## Layers

| Layer | Scope | Runs |
|---|---|---|
| Unit | engine modules (classification logic, verification pipeline, manifest store, envelope serialization) | every PR, local + CI |
| Integration | engine against real NTFS paths in temp directories; probe-file behavior with synthetic data | every PR, local + CI |
| Contract | CLI envelope: golden JSON + schema validation per command; exit codes | every PR, local + CI |
| GUI smoke | launch, enumerate visible state, exercise one engine round trip, no crash | per release ([#9](https://github.com/turinglambdaai/fileboundary/issues/9)) |
| Manual recovery protocol | the six-stage workflow of [recovery-workflow.md](recovery-workflow.md) on the real machine | by the operator, recorded in the audit log |

Some diagnostics can only produce full results elevated on the real machine. CI and non-elevated runs must still exercise them in degraded mode and assert the `requiresElevation` reporting path — degraded behavior is itself tested behavior.

## Fixtures

- **Synthetic only.** All fixtures are generated by a checked-in generator with pinned seeds. The repository never contains real encrypted production files or personal data. One recorded exception: [`tests/fixtures/real-samples/`](../tests/fixtures/real-samples/README.md) holds a single real encrypted specimen committed by explicit owner decision ([ADR-0003](decisions/ADR-0003-real-encrypted-sample-exception.md)), pinned by its SHA-256 in `baseline.json`; the exception is file-specific and does not generalize.
- **Plaintext corpus** — small known files (text, valid minimal PDF, valid ZIP) with pinned SHA-256 values.
- **Encryption-like corpus** — high-entropy blobs, known-wrapper format samples, extension/structure mismatches — covering every classification label in [architecture.md](architecture.md#inventory-module--planned-4).
- **Round-trip baseline** — where the transparent-encryption mechanism is available on the operator's machine: known plaintext written through it, hash recorded, kept **outside** the repository and referenced by hash in tests.

## Red/green rule

Bug fixes land with two pieces of evidence in the PR: the new test failing against the unfixed code (red), and passing after the fix (green). No red, no proof the test tests anything; no green, no fix.

## Output-side scanning

For leak- and serialization-class bugs, the defense scans **produced artifacts** — manifests, reports, audit logs, envelope output — rather than matching source code. Tests assert that artifacts contain hashes, paths, and verdicts, and never file content or key material.

## CI gates

From #6 onward: a `windows-latest` workflow runs build + unit + integration + contract tests on every PR. Red CI blocks merge (required status check). The workflow may not use `continue-on-error`, skipped jobs, or weakened assertions to appear green — a workflow that cannot fail is not a gate.

Until CI exists, every PR must include the full local test command and its output as review evidence.

## Honesty rules

- Local green must reproduce on CI; a pass that only exists locally is not evidence of mergeability.
- Flaky tests are quarantined with a tracked issue and a timeout for repair — never silently skipped.
- Fabricating or reusing test output is an engineering incident per [`AGENTS.md`](../AGENTS.md).
