# Testing

Testing is the project's evidence system. The rules here are enforced in review ([`AGENTS.md`](../AGENTS.md)); from [Issue #6](https://github.com/turinglambdaai/fileboundary/issues/6) onward they are enforced by CI.

## Layers

| Layer | Scope | Runs |
|---|---|---|
| Unit | engine modules (classification logic, verification pipeline, manifest store, envelope serialization) | every PR, local + CI |
| Integration | engine against real NTFS paths in temp directories; probe-file behavior with synthetic data | every PR, local + CI |
| Contract | CLI envelope: golden JSON + schema validation per command; exit codes | every PR, local + CI |
| GUI smoke | launch, enumerate visible state, exercise one engine round trip, no crash | per release ([#9](https://github.com/turinglambdaai/fileboundary/issues/9)) |
| Manual recovery protocol | the six-stage workflow of [recovery-workflow.md](recovery-workflow.md) on the real machine | by the operator, recorded in the audit log |

Some diagnostics can only produce full results elevated on the real machine. CI and non-elevated runs must still exercise them in degraded mode and assert the `requiresElevation` reporting path — degraded behavior is itself tested behavior.

## Fixtures

- **Synthetic only.** All fixtures are generated by a checked-in generator with pinned seeds. The repository never contains real encrypted production files or personal data. Recorded exceptions in [`tests/fixtures/real-samples/`](../tests/fixtures/real-samples/README.md): a single real encrypted specimen ([ADR-0003](decisions/ADR-0003-real-encrypted-sample-exception.md), pinned in `baseline.json`; owner-requested removal deferred, see [ADR-0004](decisions/ADR-0004-real-sample-twin-pair-and-deferred-removal.md)) and a same-content encrypted/plaintext twin pair ([ADR-0004](decisions/ADR-0004-real-sample-twin-pair-and-deferred-removal.md), pinned in `baseline-twins.json`). The exception is file-specific (pinned by SHA-256) and does not generalize.
- **Plaintext corpus** — small known files (text, valid minimal PDF, valid ZIP) with pinned SHA-256 values.
- **Encryption-like corpus** — high-entropy blobs, known-wrapper format samples, extension/structure mismatches — covering every classification label in [architecture.md](architecture.md#inventory-module--planned-4).
- **Round-trip baseline** — where the transparent-encryption mechanism is available on the operator's machine: known plaintext written through it, hash recorded, kept **outside** the repository and referenced by hash in tests.

## Owner-approved real encrypted specimen regression

Under the single-file exception in [ADR-0003](decisions/ADR-0003-real-encrypted-sample-exception.md), `tests/real-wrapper-baseline-test.rkt` reads the existing `tests/fixtures/real-samples/esafenet-locked-sample.pdf` in **read-only** mode and checks its size, SHA-256, wrapper signature and `encrypted-recognized` classification against `baseline.json`. This asserts that the actual known wrapper is recognized **without** treating it as decrypted, or publishing bytes/content in CI output. It does not introduce or authorize any additional real documents. If provenance differs, CI fails instead of updating the baseline automatically. The result describes the view visible to the CI process, not necessarily raw encrypted disk bytes on the owner's machine.

Separately, [ADR-0004](decisions/ADR-0004-real-sample-twin-pair-and-deferred-removal.md) authorizes the same-content encrypted/plaintext twin pair (`baseline-twins.json`) for classifier and recovery-round-trip tests: the wrapped twin must classify `encrypted-recognized` from the wrapper signature (never entropy, never extension), and recovery of it must yield content containing the fingerprint `123 abc`. `baseline.json` is left untouched because the regression test above consumes it; the two baselines consolidate when ADR-0004's deferred removal of the ADR-0003 specimen is executed.

## Red/green rule

Bug fixes land with two pieces of evidence in the PR: the new test failing against the unfixed code (red), and passing after the fix (green). No red, no proof the test tests anything; no green, no fix.

## Output-side scanning

For leak- and serialization-class bugs, the defense scans **produced artifacts** — manifests, reports, audit logs, envelope output — rather than matching source code. Tests assert that artifacts contain hashes, paths, and verdicts, and never file content or key material.

## First executable Windows core suite

The headless Racket developer preview has a Windows-only workflow at `.github/workflows/windows-core.yml` which invokes Racket compilation, `raco test` on two synthetic suites and a real CLI subprocess smoke. The workflow exercises `version`, `scan`, and bounded read-only `doctor`; it verifies the JSON envelope and failure exit codes, and does **not** claim GUI, driver modification, or recovery coverage. A green run is required before merging the first code PR; an initially green codebase does not close #6 because many other layers remain.

## Authorized export comparison test boundary

`tests/recovery-test.rkt` uses synthetic E-SafeNet-like wrapper bytes and an intentionally minimal PDF-like export. It tests positive hints, known-plaintext SHA-256 matching and mismatch, still-wrapped rejection, no source writes, and refusal to promote a merely plausible file to a recovered/verified verdict. `tests/cli-test.rkt` tests the JSON status/exit-code contract. These tests **do not simulate actual E-SafeNet decryption**, full PDF validation, or vendor authorization.

## Windows CLI JSON Schema gate

The Windows core workflow installs a pinned **test-only** `jsonschema==4.23.0` Python dependency and executes `tests/validate_contract.py`. It invokes the actual Racket CLI for `version`, `scan`, `doctor`, `verify` and invalid-input cases on synthetic fixtures, validates both envelope and per-command payload schemas from `contracts/`, asserts exit-code/status consistency, and proves that removing a required key or forging a `verified` recovery verdict is rejected. Full-path and file-content leakage checks run on the emitted results.

This increases actual contract coverage but does **not** finish release packaging, persistent artifacts, independent decrypted-file verification or CI branch protection (plan limitation in Issue #6).

## CI gates

From #6 onward: a `windows-latest` workflow runs build + unit + integration + contract tests on every PR. Red CI blocks merge (required status check). The workflow may not use `continue-on-error`, skipped jobs, or weakened assertions to appear green — a workflow that cannot fail is not a gate.

Until CI exists, every PR must include the full local test command and its output as review evidence.

## Honesty rules

- Local green must reproduce on CI; a pass that only exists locally is not evidence of mergeability.
- Flaky tests are quarantined with a tracked issue and a timeout for repair — never silently skipped.
- Fabricating or reusing test output is an engineering incident per [`AGENTS.md`](../AGENTS.md).
