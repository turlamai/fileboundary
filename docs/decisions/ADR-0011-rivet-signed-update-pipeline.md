# ADR-0011: rivet signed update pipeline and family update behavior

- **Status:** accepted
- **Date:** 2026-11-08
- **Deciders:** owner (turlamai), directive "在线更新请参考 taskly 这个标杆程序"
- **Revises:** [ADR-0008](ADR-0008-release-channel-and-self-update.md) (explicit-network-only checks; SHA-256-only integrity; self-built manifest format)
- **Revises:** [ADR-0010](ADR-0010-windows-msi-install-face.md) (deferral of the signed manifest)

## Context

ADR-0008 specified a self-built update channel: a SHA-256-only `manifest.json`
published next to the release assets, consumed by a bespoke engine module, with
the promise that *every* network access is operator-initiated. ADR-0010 accepted
the MSI as the primary install face but deferred signature verification. The
result left the GUI able to *report* an update but unable to deliver one — the
operator is told to walk to the GitHub Releases page and download an MSI by
hand — and the channel had no protection against a tampered feed beyond the
artifact hashes themselves being trusted from the same unauthenticated
manifest.

The family precedent is taskly, whose online updates the owner named as the
benchmark: `raco rivet` ships the whole transfer pipeline as a library — an
Ed25519-signed channel manifest (authenticate-before-parse), a deadline-bounded
downloader with stall/total watchdogs, a cancelable phase state, a sticky
per-install rollout bucket, and (on Windows) the `MsiHandoff` quit→msiexec→
relaunch batch. fileboundary's pinned rivet already contained all of it unused.

## Decision

1. **The update channel switches to rivet's signed pipeline.** The feed is
   `update-stable.json` (rivet signed-manifest wrapper, Ed25519, key id
   `fileboundary-2026-11`, trust root embedded in `app/update.rkt`); release
   builds run `raco rivet release` *with* updates enabled; the self-built
   `manifest.json` / full-package channel and `tools/make_update_manifest.py`
   are retired without a compatibility shroud — old clients get an honest
   fetch failure (no compatibility layers for hypothetical stock, per the
   standing release rules).
2. **Update behavior matches the family contract** (`docs/update-contract.md`):
   a silent launch check 3 s after startup, throttled to one attempt per 4 h
   by a persisted stamp the backend writes when a check *settles*; a manual
   check that bypasses throttle and toggle; an auto-check toggle (default on);
   nothing downloads before an explicit consent; downloads run with progress
   and cancel; installation is a separate, explicit quit-and-install step.
3. **Network clause of ADR-0008 is revised accordingly**: network access is no
   longer exclusively operator-initiated, but it is still bounded to the
   update feed, silent checks are throttled and off-switchable, and there is
   still no background traffic, telemetry or upload of any kind.
4. **Installation stays host-owned on both Windows faces**: MSI installs via
   rivet `MsiHandoff` (passive msiexec upgrade, one UAC consent, relaunch);
   portable zip installs via the family zip-swap handoff batch (extract and
   verify *before* touching the running copy, `.old` fallback rollback,
   success/failure markers reported on next launch).
5. **Key material**: the Ed25519 keypair is generated by
   `scripts/update-keys.sh`; the private PEM lives only in the operator's key
   directory and the GitHub secret `RIVET_UPDATE_PRIVATE_KEY`;
   `scripts/check-release-signing-key.sh` proves the signing key matches the
   embedded trust root before packaging and again before publication.

## Consequences

- The GUI can deliver an update end to end: check → consent → download with
  progress/cancel → install consent → quit-and-install → version swapped with
  rollback on failure.
- `update now` on the CLI keeps a meaningful role (check + verified download)
  but installation is host-owned; `update apply` is retired with the channel.
- Old builds' check button will 404 against the retired feed; the error text
  points at the Releases page, which remains the manual fallback for any
  version.
- Key rotation ships a build trusting the next key first (dual-trust window
  via `#:trusted-keys`, rivet 0.14+).
